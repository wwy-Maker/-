## 1. 关键路径与并行策略

### 1.1 关键路径（Critical Path）

14 个关键路径 Story，决定最小可验证单元能否跑通：

```
S01 → S03 → S05 → S06 → S07 → S08 → S14 → S15
                                              ↓
S01 → S10 → S11 → S21 → S24 → S26（教学波集成）
                ↑
S06 → S13 → S16 → S17 → S26
        ↑
S14 → S18 → S26
```

### 1.2 并行窗口

| 并行窗口 | 可同时进行的 Story | 前置条件 |
|---------|-------------------|---------|
| 窗口A | S02 ∥ S03 ∥ S05 | S01 完成 |
| 窗口B | S04 ∥ S06 ∥ S07 ∥ S08(等S03+S07) ∥ S09 ∥ S10 ∥ S13 ∥ S14(等S03+S07) | 窗口A完成 |

| 窗口D | S21 ∥ S24 ∥ S25 | 窗口C完成 |
| 终点 | S26（集成） | 全部P0 Story完成 |

### 1.3 一人+AI工具链的推荐执行顺序

一人开发无法真正并行，但有"配置先行"策略可优化：

**第1波（地基，~12h）**：S01 → S02 ∥ S03 ∥ S05 → S04 ∥ S06 → S07
**第2波（核心系统，~15h）**：S08 ∥ S09 ∥ S10 → S11 ∥ S12 ∥ S13 ∥ S14
**第3波（战斗系统，~12h）**：S15 ∥ S16 ∥ S17 ∥ S18 ∥ S19 ∥ S20 ∥ S22 ∥ S23
**第4波（集成层，~10h）**：S21 → S24 → S25 → S26

### 2.2 需注意的差异

#### 差异1：Boss阶段切换阈值

| 来源 | 阈值 |
|------|------|
| 文策渊UX规格 | 50% HP（两阶段时间大致相等） |
| 程基岩Epic拆分 S30 | 60% HP（P2）/ 30% HP（P3） |

**处置**：程基岩的 S30 配置是3阶段完整版（100%→60%→30%）。Demo 只有儒宗师阶段1-2，实际只用到1个切换点。建议 Demo 阶段切换点取 **50% HP**（文策渊建议），S30 的3阶段配置保留为正式版数据，Demo 中 bosses.json 只填阶段1-2数据。

#### 差异2：器物店触发时机

| 来源 | 设定 |
|------|------|
| 文策渊UX规格 | 建议波2后触发（因Demo只有1Boss） |
| 程基岩Epic拆分 S38 | Boss1后→Shop→Boss2→Boss3 |
| **用户决策** | **Demo不做器物店触发** |

**处置**：
- S43(items.json)、S44(ItemSystem)、S45(Shop UI) 仍产出（数据定义+UI原型），但不嵌入 Demo 游戏流程
- S38 的完整流程（Boss1→Shop→Boss2→Boss3）在 Demo 中简化为：Wave1-5 → Boss(儒宗师阶段1-2) → VictoryScreen
- S42 Bootstrapper 集成时跳过 Shop 状态转换

**配置校验测试**（ConfigValidationTests.cs）——S05+S06 完成后立即编写：
- 验证 JSON 格式正确
- 验证必填字段齐全

### 5.3 VDD 流程

```
1. 读 Story 验收标准
2. 先写测试（红灯——测试失败因为功能未实现）
3. 实现功能代码（绿灯——测试通过）
4. 重构（保持绿灯）
5. 测试结果存入 Tests/results/<story-id>/
```
